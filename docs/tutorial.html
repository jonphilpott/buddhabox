1. Framework Overview

BuddhaBox is a generative ambient audio system built entirely from scratch on a STM32F401CC "Black Pill" microcontroller. There is no operating system, no audio middleware, and no scheduler. It is bare-metal C++ all the way down.

The design goal is a modular synthesizer in code: independent DSP building blocks (oscillators, filters, envelopes, delay lines) that are wired together in a single audioCallback() function to create an evolving sonic patch. Adding a new effect means instantiating a module and connecting its output to an input — exactly like patching a hardware modular synth.

Here is the full pipeline from power-on to speaker:

setup() → AudioEngine::begin() → I2S + DMA started → audio flows forever
DMA interrupt (44100× per second, in pairs of 256-sample blocks):
audioCallback() → DSP modules → int16_t buffer → I2S peripheral → UDA1334A DAC → Speaker

The key architectural insight is the separation of concerns:

  • audio_engine.cpp — owns all hardware setup (GPIO, I2S, DMA). You never need to touch it unless you change pins or sample rate.
  • DSP headers — pure math, no hardware dependencies. Each module is self-contained and testable in isolation.
  • main.cpp — the "patch": declares module instances, wires them together in audioCallback(), and configures parameters in setup().

2. Hardware Platform

The STM32F401CC "Black Pill"

The Black Pill is a compact development board built around ST Microelectronics' STM32F401CC chip. Key facts relevant to audio:

  • CPU: 84 MHz ARM Cortex-M4 with hardware floating-point unit (FPU). The FPU handles 32-bit float operations in a single clock cycle, which is why the whole DSP layer uses float instead of fixed-point arithmetic.
  • RAM: 64 KB SRAM. This constrains how large delay buffers can be. The DMA audio buffer costs 2 KB, leaving ~62 KB for DSP state and delay lines.
  • Flash: 256 KB. Since all DSP modules are header-only and inlined, the compiled code is relatively compact.
  • I2S peripheral: A dedicated serial audio interface, built into the SPI2 block. This is what clocks audio bits out to the DAC.
  • DMA controller: Offloads data transfer from RAM to I2S without involving the CPU. Critical for uninterrupted audio.
  • ADC: 12-bit analog-to-digital converter, used to read sensors. Not usable from the audio ISR (too slow).

The UDA1334A DAC

The UDA1334A is a stereo I2S DAC from NXP. It accepts a digital audio stream and produces an analog voltage that drives the speakers. It supports 16-bit stereo audio at sample rates up to 96 kHz — we use 44.1 kHz (CD quality).

The Light Sensor (LDR)

A photoresistor (LDR) is connected to analog pin PA0. Its resistance changes with ambient light. The firmware reads this via AnalogInput and uses the value to modulate parameters — brighter light produces brighter, more active music; darkness produces darker, slower music. This is the primary way the physical environment feeds into the generative system.

3. The I2S Protocol

I2S (Inter-IC Sound) is a simple serial bus for transmitting stereo audio between chips. Understanding it helps you understand why the DMA buffer is structured the way it is.

Three Wires, One Stereo Stream

I2S carries stereo audio using just three signals:

  • BCLK (Bit Clock): The master clock that ticks once per bit. At 44100 Hz stereo 16-bit audio, BCLK runs at 44100 × 2 channels × 16 bits = 1,411,200 Hz (1.4 MHz).
  • WSEL (Word Select / LRCLK): Toggles at the sample rate (44100 Hz). When WSEL is low, the next 16 bits are the left channel; when high, the right channel.
  • DIN (Data In): The audio bits are shifted out MSB-first on every BCLK edge.

How the STM32 Configures I2S

In audio_engine.cpp, the I2S peripheral is configured via the STM32 HAL library in a series of steps:

  1. PLLI2S clock configuration: The I2S peripheral cannot use the main system clock directly — it needs its own dedicated PLL (Phase Locked Loop) that generates a precise frequency. The BuddhaBox configures PLLI2SN=192 and PLLI2SR=2 to derive the correct 44.1 kHz sample rate. Getting this wrong produces silence or the wrong pitch.
  2. Peripheral clocks enabled: SPI2 (which contains I2S2), DMA1, and GPIOB clocks are all gated on.
  3. GPIO pins configured: PB12, PB13, PB15 are set to Alternate Function mode with the SPI2 alternate function (GPIO_AF5_SPI2). This routes the I2S signals to those physical pins.
  4. I2S peripheral initialized: Master TX mode, Philips standard, 16-bit data format, no MCLK output.
  5. DMA configured and started.

Why I2S Is Shared With SPI2

ST's STM32F4 chips implement I2S inside the SPI peripheral block — they share the same hardware registers. The peripheral is switched into I2S mode at init time. This is why you see SPI2 in the source code even though we're doing audio, not SPI.

4. DMA and the Double-Buffer Pattern

What is DMA?

DMA (Direct Memory Access) is a hardware controller on the STM32 that can autonomously transfer data from one memory region to another — or from memory to a peripheral like I2S — without the CPU doing any work. This is essential for audio: if the CPU had to manually push each sample to the I2S hardware, it would spend all its time doing that instead of computing the next sample.

With DMA, the CPU sets up a transfer once and then is free to compute audio samples while the DMA feeds the I2S peripheral in the background.

Circular Mode

DMA is configured in circular mode. When it reaches the end of the buffer, it automatically wraps back to the beginning and continues — forever. This creates a continuous, uninterrupted audio stream.

The Double-Buffer Ping-Pong

The DMA buffer is split into two equal halves. This is the key trick that allows the CPU and DMA to work simultaneously without ever touching the same memory at the same time:

Half A — DMA Playing DMA is reading from this half
and clocking it to I2S
Half B — CPU Filling audioCallback() is computing
new samples into this half

The DMA fires two interrupts per buffer cycle:

  • Half-complete interrupt: DMA has finished playing Half A and is now playing Half B. The CPU fills Half A with new samples.
  • Full-complete interrupt: DMA has finished playing Half B and wraps back to Half A. The CPU fills Half B.

This ping-pong repeats at a rate of 44100 / 256 ≈ 172 times per second. Each callback fills 256 stereo frames, which takes about 5.8 ms. As long as audioCallback() completes in under 5.8 ms, the audio is gapless.

Warning — Timing Budget At 84 MHz, 5.8 ms equals about 487,000 CPU cycles. That sounds like a lot, but a naive sinf() call takes roughly 200 cycles. With 256 samples and multiple modules, the budget disappears quickly. This is why the framework uses wavetables, fast approximations, and control-rate dividers.

Buffer Layout in Memory

The DMA buffer is declared as:

static int16_t dmaBuffer[AUDIO_BLOCK_SIZE * 2 * 2];
// = 256 frames × 2 channels × 2 halves = 1024 int16_t = 2048 bytes

Memory layout:

dmaBuffer[0..1023]
indices 0–511
Half A: 256 stereo frames
[L,R,L,R,...] × 256 indices 512–1023
Half B: 256 stereo frames
[L,R,L,R,...] × 256

The interrupt handlers in audio_engine.cpp map directly onto this:

// Called when DMA finishes Half A — fill Half A (starting at index 0)
extern "C" void HAL_I2S_TxHalfCpltCallback(I2S_HandleTypeDef *hi2s) {
  audioCallback(dmaBuffer, AUDIO_BLOCK_SIZE * 2);
}

// Called when DMA finishes Half B — fill Half B (starting at index 512)
extern "C" void HAL_I2S_TxCpltCallback(I2S_HandleTypeDef *hi2s) {
  audioCallback(dmaBuffer + AUDIO_BLOCK_SIZE * 2, AUDIO_BLOCK_SIZE * 2);
}

5. The Audio Callback

The audioCallback() function is the heart of everything. It runs in interrupt context — meaning it preempts the main loop and must finish before the DMA needs the buffer again.

Signature and Buffer Format

void audioCallback(int16_t *buffer, uint16_t length) {
  for (uint16_t i = 0; i < length; i += 2) {
    // compute one stereo frame here...
    float leftSample  = /* ... */;
    float rightSample = /* ... */;

    // convert float [-1.0, +1.0] → int16_t [-32000, +32000]
    buffer[i]     = (int16_t)(leftSample  * 32000.0f);
    buffer[i + 1] = (int16_t)(rightSample * 32000.0f);
  }
}

The buffer is stereo interleaved: each pair of int16_t values is one stereo frame — [Left, Right, Left, Right, ...]. The loop steps by 2 (i += 2) so each iteration handles one frame. length will always be AUDIO_BLOCK_SIZE × 2 = 512.

The Float-to-Integer Conversion

All internal DSP math uses float normalized to -1.0 to +1.0. The conversion to int16_t happens exactly once, at the very last step. We multiply by 32000 rather than 32767 to leave a few counts of headroom before integer overflow — a safety margin for transients.

6. DSP Module Design Principles

Every module in the BuddhaBox framework follows the same set of conventions. Understanding these conventions lets you add new modules without surprises.

The process() Pattern

Every module exposes one core method: process(). It is called exactly once per audio sample inside the callback loop. It advances the module's internal state by one sample and returns (or updates) the output:

// Source modules: no input, generate a signal
float sample = osc.process();   // returns next sample

// Processing modules: take input, return output
env.process(inputSample);       // updates internal state
float out = env.lowpass();      // read the result

// Multiplier (envelope shaping):
float audio = osc.process() * env.process();

Header-Only for Inlining

All DSP modules live in .h files with their implementations directly in the class body. This allows the C++ compiler to inline the code at the call site — eliminating function-call overhead for small, frequently-called methods like process(). At 44100 calls per second, even the cost of a function call register save/restore adds up.

Float Normalization: The -1.0 to +1.0 Contract

All audio signals flowing between modules must stay in the range -1.0 to +1.0. This is not enforced at every step — it's a design contract. Benefits:

  • You can sum signals by addition: mix = a + b, then scale down: mix * 0.5f
  • Multiplication is always modulation: osc.process() * env.process() applies the envelope as an amplitude shape
  • The final int16 conversion is a predictable single multiply

No Dynamic Allocation

Everything is allocated at compile time — global or static instances. This avoids heap fragmentation (a serious problem in embedded systems where RAM is scarce and there's no garbage collector) and guarantees that all memory is available before setup() runs. Delay lines, oscillators, filters — all declared as globals in main.cpp.

dsp_common.h — The Foundation

This header is included by every module. It provides:

  • SAMPLE_RATE (44100) and AUDIO_BLOCK_SIZE (256) — constants used everywhere to convert between time and samples
  • PI_F and TWO_PI_F — float versions of π to avoid implicit double conversions
  • clampf(x, lo, hi) — constrain a value to a range
  • lerpf(a, b, t) — linear interpolation, used in wavetables and delay reads
  • mapf(x, inLo, inHi, outLo, outHi) — rescale from one range to another
  • softclip(x, drive) — gentle saturation using a fast tanh approximation
  • fastSin(x) — parabolic sine approximation, ~4× faster than sinf()

7. Oscillators — The Phase Accumulator

An oscillator generates a periodic waveform at a given frequency. The BuddhaBox uses the phase accumulator pattern, which is the standard approach in digital synthesis.

The Core Idea

Instead of tracking elapsed time in seconds (which requires division), we maintain a phase variable that ramps from 0.0 to 1.0 and wraps. One full 0→1 cycle equals one period of the waveform. The speed of this ramp is the phase increment:

// phaseIncrement = how far phase advances each sample
phaseInc_ = frequency / SAMPLE_RATE;

// For 440 Hz at 44100 Hz sample rate:
// phaseInc = 440 / 44100 ≈ 0.00998
// Phase completes one 0→1 cycle in ~100 samples

This is elegant because the phase stays bounded (no accumulating float precision errors), and changing frequency just means changing the increment.

Waveform Generation from Phase

Given phase in [0, 1), computing each waveform is straightforward:

WaveformFormulaHarmonicsCharacter
Sine Wavetable lookup (see below) Fundamental only Pure, smooth, mellow
Saw 2.0 × phase − 1.0 All harmonics (1/n) Bright, buzzy, rich
Square phase < 0.5 ? +1 : −1 Odd harmonics (1/n) Hollow, clarinet-like
Triangle Two linear segments Odd harmonics (1/n²) Softer than square

The Sine Wavetable

Computing sinf() every sample is expensive (~200 cycles on M4). Instead, the Oscillator class pre-computes a table of 512 sine values once at startup and performs a fast table lookup plus linear interpolation on each sample:

// At startup (runs once):
for (uint16_t i = 0; i < SINE_TABLE_SIZE; i++)
  table[i] = sinf(TWO_PI_F * i / SINE_TABLE_SIZE);

// Per sample (~3 multiply-add operations on the FPU):
float fIdx = phase * SINE_TABLE_SIZE;   // e.g., 128.7
uint16_t i0 = (uint16_t)fIdx;          // 128
float frac = fIdx - i0;                  // 0.7
uint16_t i1 = (i0 + 1) & (SINE_TABLE_SIZE - 1); // 129 (wraps at 511→0)
return table[i0] + frac * (table[i1] - table[i0]); // lerp

The 512-entry table gives interpolation error below -96 dB — the noise floor of 16-bit audio. The table is shared across all Oscillator instances via a C++ Meyer's singleton static, so it only costs 2 KB of RAM regardless of how many oscillators are running.

8. LFOs — Low Frequency Oscillators

An LFO is structurally identical to an Oscillator — it's a phase accumulator generating a periodic waveform — but it operates at sub-audio frequencies (typically 0.01 to 20 Hz). Instead of making sound, its output is used to modulate other parameters over time.

LFO as a Modulation Source

The LFO outputs a signal in [-1.0, +1.0]. You scale and offset it to the target parameter's range using mapf():

// LFO sweeping filter cutoff from 500 Hz to 3000 Hz:
float mod = filterLFO.process();  // -1.0 to +1.0
float cutoff = mapf(mod, -1.0f, 1.0f, 500.0f, 3000.0f);
filter1.setFrequency(cutoff);

Common modulation targets in BuddhaBox:

  • Filter cutoff — makes the tone breathe and evolve
  • Delay time — creates subtle chorus/pitch-shifting on echoes
  • Delay feedback — makes the echo tail dynamically shorter/longer
  • Another LFO's depth — the "filterLFOLFO" slowly shifts how high the main LFO sweeps

Control-Rate Dividers

LFOs are often too slow to justify computing every sample. A filter cutoff moving at 0.025 Hz changes by roughly 0.025 / 44100 ≈ 0.0000006 per sample — utterly imperceptible. The setDivider(n) method makes the LFO recompute only once every n samples and return the cached value in between:

filterLFO.setDivider(64);  // Recompute ~689 times/sec instead of 44100
                             // 64× fewer sinf() calls in SVFilter

The frequency stays exact: when the LFO does recompute, it advances its phase by phaseInc × divider to account for all the skipped samples.

9. Filters — The State Variable Filter

Filters are the soul of synthesis. They sculpt the frequency content of a signal — cutting some frequencies while passing others — turning raw waveforms and noise into expressive, shaped sound. The BuddhaBox uses the Chamberlin State Variable Filter (SVF), chosen because it simultaneously computes all three common filter responses from a single pass of arithmetic.

What Filters Do, Intuitively

Imagine a signal is composed of many sine waves at different frequencies all playing at once (this is literally what Fourier analysis tells us). A filter is a device that lets some of those sine waves through unchanged while attenuating (reducing) others. Three fundamental types:

  • Lowpass: Passes frequencies below the cutoff. Blocks high frequencies. Sounds warm, dark, muffled — like hearing music through a wall.
  • Highpass: Passes frequencies above the cutoff. Blocks low frequencies. Sounds thin, bright, airy — like a small tinny speaker.
  • Bandpass: Passes frequencies near the cutoff. Blocks both high and low frequencies. Sounds focused, vowel-like, nasal.

A notch (band-reject) filter can be synthesized by adding the lowpass and highpass outputs together.

The Chamberlin SVF Algorithm

The SVF is a recursive digital filter — each output sample depends on previous outputs. It maintains three state variables (lp_, hp_, bp_) that are updated every sample. The update equations per sample are:

1.  lp  +=  f  ×  bp   integrate bandpass → lowpass
2.  hp  =  input  -  lp  -  damp  ×  bp   remainder = highpass
3.  bp  +=  f  ×  hp   integrate highpass → bandpass

Where:

  • f = 2 × sin(π × cutoff / sampleRate) — the frequency coefficient. Controls how fast the integrators respond. Small f = low cutoff, large f = high cutoff.
  • damp = 2 × (1 − resonance) — the damping factor. Low damping = high resonance peak.

Why Three Integrators?

Think of the SVF as a feedback system. The lowpass integrates the bandpass — it's like counting up the total area under the bandpass signal, which is a mathematical way of blurring out rapid changes. The highpass is what's "left over" after the lowpass and resonance feedback are subtracted. The bandpass then integrates the highpass — which means it sits in the middle. Together these three form a closed loop that acts as a tuned resonator.

Here's the code, directly from filter.h:

void process(float input) {
  lp_ += f_ * bp_;                    // Step 1: lowpass integrates bandpass
  hp_ = input - lp_ - damp_ * bp_;   // Step 2: highpass is the remainder
  bp_ += f_ * hp_;                    // Step 3: bandpass integrates highpass
}

Three multiplications and three additions per sample. This is extraordinarily cheap for the sonic result it produces.

Resonance

The damp_ term in step 2 controls how much of the bandpass signal is subtracted from the highpass. A high damp value (low resonance) dissipates energy quickly — gentle rolloff. A low damp value (high resonance) allows more energy to circulate in the feedback loop, producing a peak in the frequency response at the cutoff. At zero damping, the filter self-oscillates and produces a sine wave at the cutoff frequency — the classic synthesizer "screaming filter."

Stability Constraint The Chamberlin SVF becomes numerically unstable when the cutoff approaches half the sample rate (Nyquist = 22050 Hz). The code clamps the cutoff to SAMPLE_RATE / 4 = 11025 Hz to stay safely below this limit. For ambient music this is never a practical constraint.

Frequency Coefficient Caching

Computing sinf() for the frequency coefficient is expensive. Since setFrequency() is called every sample when driven by an LFO, but the LFO uses a control-rate divider (returning the same float value for 64 consecutive samples), the filter caches the last frequency value and skips the sinf() when nothing has changed:

if (hz == lastHz_) return;   // identical bits → skip sinf()
lastHz_ = hz;
f_ = 2.0f * sinf(PI_F * hz / SAMPLE_RATE);

This is one of the rare legitimate uses of exact float equality comparison — we're comparing our own cached value against itself, not two independently computed results.

Using the SVF in Practice

In main.cpp, three SVFilter instances are used differently:

  • filter1 — main lowpass on the summed melody+noise signal, swept by filterLFO
  • noise_filter — bandpass on the pink noise source to give it texture and sweep
  • output_highpass — static highpass at 180 Hz to remove sub-bass rumble and DC offset from the final output

10. Envelopes — Shaping Sound Over Time

Without an envelope, an oscillator produces a constant drone. An envelope shapes how a sound's amplitude changes from the moment it starts to when it fades away. The BuddhaBox implements an AR (Attack-Release) envelope with exponential curves.

States

IDLE ──gate(true)──→ ATTACK ──reaches 1.0──→ SUSTAIN ──gate(false)──→ RELEASE ──fades to 0──→ IDLE
  trigger() mode: ATTACK → RELEASE (no SUSTAIN — auto-releases after attack)

Exponential Curves — Why They Sound Natural

Human hearing is logarithmic. We perceive a doubling of sound energy as a roughly equal perceptual step. A linear ramp (constant amount per sample) sounds like it speeds up near the top of the attack and lingers too long at the start of release. An exponential curve (constant ratio per sample) sounds smooth and even because it matches our perceptual scale.

The implementation uses an exponential approach toward the target:

// Attack: exponential approach toward 1.0
value_ = attackCoeff_ * value_ + (1.0f - attackCoeff_) * 1.0f;

// Release: exponential decay toward 0.0
value_ *= releaseCoeff_;

The coefficients are computed from the desired time using:

attackCoeff_  = expf(-5.0f / (seconds * SAMPLE_RATE));
releaseCoeff_ = expf(-5.0f / (seconds * SAMPLE_RATE));

The -5.0 constant ensures the envelope reaches approximately 99% of its target in the requested time (rather than just 63% which a time constant tau approach would give). This matches user intuitions better.

Two Trigger Modes

  • gate(true) / gate(false): Explicit note-on/note-off. Attack when gate opens, release when it closes. Used for sustained sounds.
  • trigger(): One-shot mode. Attacks from current level then automatically transitions to Release — no Sustain phase. Used for percussive hits in BuddhaBox, as the tung drum note fires and immediately begins decaying.

The BuddhaBox uses two envelope instances — one for the percussive tung drum melody (env, fast attack + randomized short release) and one for the slow arpeggio swell (arp_env, 4-second attack + 18-second release).

11. Delay Lines — Memory of the Past

A delay line stores a history of audio samples and lets you read them back after a specified time. It is one of the most versatile DSP primitives, underlying echo, chorus, flanger, and Karplus-Strong string synthesis.

The Circular Buffer

The naive implementation of a delay would shift all samples in an array forward by one position each sample — an O(N) operation for a buffer of length N. At 44100 Hz, this would be catastrophically slow for any useful delay time.

Instead, the DelayLine uses a circular buffer with a moving write pointer. Writing a sample advances the pointer; reading a sample from N steps ago means looking at (writePos − N), wrapping around if necessary. Both operations are O(1):

// Write: store sample, advance pointer
buffer_[writePos_] = (int16_t)(sample * 32767.0f);
writePos_ = (writePos_ + 1) % MAX_SAMPLES;

// Read: look backward from write position
float pos = (float)writePos_ - delaySamples - 1.0f;
if (pos < 0.0f) pos += MAX_SAMPLES;  // wrap

int16_t Storage — Halving RAM Cost

Samples are stored as int16_t (2 bytes) rather than float (4 bytes), cutting the RAM requirement in half. The API still accepts and returns float — conversion happens at the boundary. The quantization noise introduced by 16-bit storage is -96 dB, well below the noise floor of the final 16-bit output.

Fractional Delay and Linear Interpolation

When the delay time is not a whole number of samples (e.g., 100.7 samples), simply rounding to the nearest integer introduces a small pitch error and causes audible "stepping" artifacts when the delay time is modulated. Linear interpolation between the two nearest samples solves this:

uint16_t idx0 = (uint16_t)pos % MAX_SAMPLES;
uint16_t idx1 = (idx0 + 1) % MAX_SAMPLES;
float s0 = (float)buffer_[idx0] / 32767.0f;
float s1 = (float)buffer_[idx1] / 32767.0f;
float frac = pos - floorf(pos);        // 0.0–1.0: fractional part
return lerpf(s0, s1, frac);            // blend between neighbours

Echo with Feedback

The BuddhaBox delay patch applies an echo to the melodic elements with LFO-modulated feedback and delay time:

float dlfo     = delayLFO.process();
float delay_fb = mapf(delayFeedbackLFO.process(),
                      -1.0f, 1.0f,
                      delay_feedback_min, delay_feedback_max);
float delayed  = delay1.read(
                    mapf(dlfo, -1.0f, 1.0f,
                         delay_time_min, delay_time_max));
delay1.write(sample + delayed * delay_fb); // feedback loop

Modulating delay time with an LFO causes subtle pitch shifting (like a chorus effect) on the echoes, making the delay feel alive and breathing rather than mechanical.

Template Parameter

DelayLine is a C++ template class: template <uint16_t MAX_SAMPLES = 4096>. The buffer size is a compile-time constant, so no heap allocation is needed. In main.cpp, the delay is declared as DelayLine<20000> delay1 — about 453 ms at 44.1 kHz, costing 40 KB of RAM.

12. Noise Generation

Noise is essential for ambient texture. Two generators are provided.

White Noise — xorshift32

WhiteNoise uses a xorshift32 pseudo-random number generator: three XOR-and-shift operations on a 32-bit state. It produces a sequence of 2³² − 1 values before repeating — at 44100 Hz that's about 27 hours. It runs in roughly 3–5 CPU cycles per sample:

state_ ^= state_ << 13;
state_ ^= state_ >> 17;
state_ ^= state_ << 5;
return (float)(int32_t)state_ / 2147483648.0f; // → [-1, +1]

White noise has equal energy per frequency band — it sounds harsh and "hissy." Useful for creating "air" and high-frequency texture when mixed subtly.

Pink Noise — Voss-McCartney Algorithm

Pink noise has equal energy per octave — it rolls off at −3 dB per octave and sounds much more natural (rain, wind, ocean). The Voss-McCartney algorithm achieves this by maintaining 12 "rows" of random values, each updated at a progressively lower rate:

  • Row 0: updated every sample (highest octave, fastest)
  • Row 1: updated every 2 samples
  • Row 2: updated every 4 samples
  • …
  • Row 11: updated every 2048 samples (lowest octave, slowest)

The output is the sum of all rows divided by 13. Because each row contributes equal variance but at a lower frequency, we get equal energy per octave. The clever trick for scheduling is to use the trailing zeros of a counter to determine which row to update — an O(1) operation:

counter_++;
// Trailing zeros tell us which row to update:
// counter=1 → 0 trailing zeros → row 0 (every sample)
// counter=2 → 1 trailing zero  → row 1 (every 2 samples)
// counter=4 → 2 trailing zeros → row 2 (every 4 samples)
int numZeros = __builtin_ctz(counter_) ...  // (simplified)

runningSum_ -= rows_[numZeros];
rows_[numZeros] = white_.process();
runningSum_ += rows_[numZeros];

A running sum avoids re-summing all 12 rows every sample — only one row changes per sample, so we subtract the old value and add the new one.

In the patch, two PinkNoise instances are used: pink_noise for the main ambient texture (run through a bandpass filter), and rain for a high-frequency rain-like layer (modulated by the rainLFO).

13. Analog Input — Reading Sensors

The AnalogInput class reads an ADC pin and smooths the result. It is designed to bridge the slow hardware world (ADC reads, physical sensors) into the fast DSP world (audio callback).

The Smoothing Problem

Raw ADC readings jitter by several counts even when the input voltage is stable — this is quantization noise from the ADC itself. If you pass a jittery ADC reading directly to filter.setFrequency(), you'll hear crackling artifacts as the filter coefficient jumps around. Smoothing eliminates this.

Exponential Moving Average (EMA)

The smoothing uses an EMA filter, which is the discrete-time equivalent of a simple RC (resistor-capacitor) lowpass filter:

smoothed_ += alpha_ * (raw - smoothed_);

At each update call, the smoothed value moves a fraction alpha of the way toward the raw reading. Small alpha = slow, smooth tracking. Large alpha = fast, noisier tracking.

Thread-Safety Trick

update() is called from loop() (the main thread). The audio callback (ISR) reads the smoothed value via read(). On ARM Cortex-M4, a 32-bit float read is a single instruction and therefore atomic — the ISR can never see a half-written value. This is why no locking is needed.

The LDR Calibration

The photoresistor uses a custom readLDR() method that maps the raw read range to a more useful 0.0–1.0 span, accounting for the actual voltage divider characteristics of the hardware. This kind of hardware-specific tuning is normal in embedded audio — the math may look odd but reflects real-world measurements:

float readLDR() const {
  float r = 1 - (read() * 5);
  float adj = r < 0.0f ? 0.0f : (r * 2.75);
  adj = adj > 1.0f ? 1.0f : adj;
  return adj;
}

Generative Events — The Clock System

BuddhaBox uses two TempoClock instances to drive musical events inside the audio callback:

  • clock — fires at the BPM rate. On each tick, it probabilistically triggers the tung drum melody and schedules parameter evolution events.
  • fast_clock — fires at a multiple of the BPM (selectable via powers of 2). Used for the arpeggio voice to select new notes rapidly.

Events are gated by random probability (rng.nextFloat() > threshold), ensuring that the music is always slightly different — never looping in exactly the same way. The LDR light sensor biases many of these probabilities, so the music responds to the physical environment.

The Colour / Scale System

The Colour class manages the musical scale and melody. It holds a set of MIDI note offsets forming a pentatonic or diatonic scale, and a melody sequence. The mixItUp() function chooses a new scale, new tempo, new melody, and re-randomizes several parameters — a "colour change" event that shifts the entire character of the music every few minutes.

Entropy Seeding

The random number generator (LFSR) is seeded from ADC noise. In setup(), 32 readings are taken from the LDR pin, XORed into the LFSR state. Subsequent entropy is injected each clock tick during playback, so the randomness never depletes.

15. Performance Considerations

Running real-time audio at 44100 Hz on an 84 MHz microcontroller requires careful attention to the cost of every operation in the inner loop. Here is how the BuddhaBox stays within budget.

Avoid sinf() in the Hot Path

sinf() takes roughly 150–200 clock cycles on the Cortex-M4 FPU. At 44100 samples/sec, one sinf() call consumes:

200 cycles × 44100 calls/sec = 8,820,000 cycles/sec

That's about 10% of the CPU budget for a single call. Mitigations:

  • Wavetable lookup: Used for oscillator sine waves — replaces sinf() with two table reads and a lerp (~5 cycles total)
  • fastSin() approximation: Used in LFO — parabolic curve, error <0.1%, ~20 cycles
  • Coefficient caching: SVFilter caches the last cutoff frequency and skips sinf() when unchanged
  • Control-rate dividers: LFOs compute only every 64 or 256 samples, so SVFilter's sinf() calls drop by the same factor

No Branching on Audio-Rate Signals

Conditional branches inside the sample loop can cause CPU pipeline stalls. DSP operations should be branchless where possible. The envelope's state machine is the main exception — but state changes are rare (only on gate events), so the branch predictor handles it well.

No I/O Inside the Callback

Serial output, I2C, SPI, and ADC reads are all performed exclusively from loop(). The lightSensor.update() call in loop() fills a float that the audio callback reads safely (atomic on ARM). This clean separation prevents priority inversion and audio glitches.

Float vs Double

The STM32F401 has a hardware FPU for 32-bit float. double operations are emulated in software and take roughly 20× longer. Every math constant in the codebase uses the f suffix (3.14159f, 0.5f) to stay in float and avoid implicit widening to double.

int16_t Delay Storage

Using int16_t in DelayLine halves the RAM cost and keeps the delay buffer in a smaller cache footprint on the M4. The quantization noise is inaudible at the application level.

Static Allocation

All objects are stack or global — no dynamic allocation. This gives the linker complete visibility into memory usage and prevents fragmentation. The linker map shows exactly how much RAM is used and raises a compile-time error if it exceeds 64 KB.

Measuring CPU Usage

To verify the audio callback is completing on time, you can toggle a GPIO pin at the start and end of the callback and measure the pulse width with an oscilloscope. If the pulse ever exceeds 5.8 ms, you have an overrun. Alternatively, watch for audio glitches — they manifest as periodic clicks or silence when the callback misses its deadline.

Tip — Adding a New Module When adding a new DSP module, estimate its cost first: count multiplications and function calls in the process() path. One heavy-weight sinf() call ≈ 200 cycles ≈ 0.2% of the 84 MHz budget at 44100 Hz. Five modules each using sinf() per sample = ~1% budget, which is fine. Twenty modules would start to push limits. Use control-rate dividers and coefficient caching aggressively.

16. How to Add New Things

Adding a New DSP Module

  1. Create a new header file in src/, e.g. src/chorus.h
  2. Add #pragma once and #include "dsp_common.h"
  3. Write the class with a process() method. Follow the sample-by-sample pattern.
  4. Declare an instance in main.cpp as a global
  5. Call module.process() at the right point in audioCallback()
  6. Configure it in setup()

Adding a New Modulation

To connect an LFO to a new parameter:

  1. Declare an LFO global instance
  2. Set its frequency, waveform, and divider in setup()
  3. In the callback: float mod = myLFO.process(); then float param = mapf(mod, -1.0f, 1.0f, lo, hi);
  4. Pass param to the target module's setter

Adding a New Hardware Input

To add a potentiometer or sensor on a new analog pin:

  1. Declare AnalogInput myKnob(PA1, 0.1f); — choose an alpha appropriate for how fast you expect the signal to change
  2. Call myKnob.update(); in loop()
  3. In the audio callback, read it: float val = myKnob.read(); — this is safe from ISR context
  4. Scale with mapf() to your parameter range

Changing the Sample Rate or Block Size

Both are defined as constexpr in dsp_common.h. The I2S peripheral clock configuration in audio_engine.cpp also needs updating — the PLLI2S values must be recalculated for the new sample rate. All DSP modules that use SAMPLE_RATE in their math (oscillators, filters, envelopes) automatically adapt because they reference the constant directly.
